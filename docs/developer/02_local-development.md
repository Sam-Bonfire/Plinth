## 2.1 Starting the Edge API (Cloudflare Workers)

The edge API is the backend serverless component. It must be running before any other component that makes API calls.

### Start Command

```bash
mise run dev:api
```

### Equivalent Manual Commands

```bash
# Method A: From root
cd apps/edge-api && pnpm wrangler dev --port 8787

# Method B: With custom port (if 8787 is occupied)
cd apps/edge-api && pnpm wrangler dev --port 8788
```

### What the Command Starts

- **Miniflare** - Cloudflare Workers runtime emulator running locally
- **D1 in-memory database** - SQLite-style database for local development (no cloud account needed)
- **Durable Object sync rooms** - WebSocket endpoints for real-time location sync
- **HTTP server** - Listening on `http://localhost:8787` (or custom port)

### Verifying Edge API is Running

```bash
curl http://localhost:8787/health
```

**Expected response**:
```json
{
  "status": "ok",
  "timestamp": 1724967890123,
  "version": "0.1.0"
}
```

### API Base URL for Local Development

All other components should point to:
```
http://localhost:8787/api/v1/*
```

### Edge API Key Endpoints (Local Dev)

| Endpoint | Method | Description |
|---|---|---|
| `/health` | GET | Health check (shown above) |
| `/api/v1/orders` | POST | Create new order (requires auth) |
| `/api/v1/orders/{id}` | GET | Retrieve order by ID |
| `/api/v1/kds/tickets` | GET | List KDS tickets |
| `/api/v1/auth/*` | Various | Authentication and JWT verification |

## 2.2 Starting the POS Client (Tauri Native Terminal)

The POS client is the frontline terminal application used by cashiers, captains, and kitchen staff.

### Start Command

```bash
mise run dev:pos
```

### Equivalent Manual Commands

```bash
# From the plinth-monorepo root
cd apps/pos-client
pnpm --filter pos-client exec tauri dev
```

**What this starts**:
- Tauri development binary (Rust + WebView)
- React 18 UI shell embedded in native window
- Local SQLite database (rusqlite with WAL mode for offline-first behavior)
- ESC/POS printer simulation (virtual printer for development)
- Background Tokio async sync daemon (sends mutations to edge API via WebSocket)
- Tauri IPC commands for React-to-Rust communication

### POS Client Interface

Upon launching, the POS will display:
- Location selection screen (choosing which restaurant site)
- Login/authentication screen (JWT token required)
- Main order-taking interface with item categories
- KDS status panel showing active tickets
- Payment processing screen

### POS Client Development Tips

- **Restart after code changes**: Tauri auto-reloads on file changes
- **Database persistence**: Local SQLite data persists between sessions (stored in `apps/pos-client/src-tauri/db/`)

<br/>

### Common POS Development Commands

| Action | Command |
|---|---|
| Reset local database | `rm -rf apps/pos-client/src-tauri/db/*.db` |
| Enable debug logging | Modify `PLINTH_ENV` env var or check Tauri log output |
| Simulate offline mode | Disconnect network; UI should gracefully degrade |
| Test printer output | Use Tauri command `print_test_page` (if available) |

## 2.3 Starting the Web Dashboard (Next.js Admin)

The back-office dashboard is used by restaurant managers and supervisors for inventory, shifts, menus, and reports.

### Start Command

```bash
mise run dev:web
```

### Equivalent Manual Commands

```bash
# From the plinth-monorepo root
cd apps/web-dashboard
pnpm exec vite dev
```

**What this starts**:
- Next.js development server (or Vite based on config)
- Ant Design 5.x component library
- Hot Module Replacement (HMR) - changes reflect instantly
- API proxy to edge API at `http://localhost:8787` (configured in `vite.config.ts` or `next.config.js`)
- Authentication middleware (dev mode may skip auth or use test tokens)

### Dashboard Access

After starting, open:
```
http://localhost:5173  (Vite default) or http://localhost:3000 (Next.js default)
```

**Default credentials** (if auth is disabled in dev mode):
- Username/Email: `admin@plinth.local`
- Password: `admin123` (check `.env` files for dev secrets)

**Or login with test JWT** generated by the test utilities.

### Dashboard Pages

Typical dashboard routes (check `apps/web-dashboard/src/app/` for current routes):

- `/` - Dashboard home/overview
- `/menu` - Menu management interface
- `/inventory` - Stock and inventory tracking
- `/shifts` - Shift opening/closing and Z-reports
- `/reports` - Sales analytics and exports
- `/staff` - Staff permissions and role management

## 2.5 Component Interaction Diagram (Local Dev)

When all components are running locally, the interaction flow is:

```mermaid
graph LR
    POS[POS Client (Tauri + React)]
    Dashboard[Web Dashboard (Next.js)]
    Edge[Edge API (Miniflare + D1)]
    
    POS -->|WebSocket+ HTTP API| Edge
    Dashboard -->|HTTP API| Edge
    
    Edge -->|SQLite D1| Edge_DB[(Local D1 In-Memory)]
    
    style Edge fill:#e3f2fd,stroke:#1976d2
    style POS fill:#e8f5e9,stroke:#2e7d32
    style Dashboard fill:#fff3e0,stroke:#fb8c00
```

### Data Flow Examples

**1. Taking an Order (POS → Edge → D1)**:
```
POS (Tauri) --certified local transaction--> Local SQLite (WAL mode)
Pos --WebSocket mutation--> Edge API (Miniflare)
Edge --batched async flush--> D1 (cloud or local)
Edge --WebSocket broadcast--> All connected POS/KDS devices
```

**2. Checking Inventory (Dashboard → Edge)**:
```
Dashboard (Next.js) --HTTP request--> Edge API (/api/v1/inventory)
Edge --query D1--> Returns stock levels
Edge --JSON response--> Dashboard React component
```

**3. KDS Ticket Update (Edge → POS)**:
```
Order settled --Edge processes--> D1 updates ticket status
Edge --WebSocket broadcast--> All connected POS/KDS devices
POS KDS panel --updates display--> Ticket: PENDING → IN_PREP → READY → BUMPED
```

## 2.6 Stopping All Development Servers

When finished for the day, stop all running processes:

| Component | Stop Method |
|---|---|
| Edge API | `Ctrl+C` in the terminal where `mise run dev:api` was run |
| POS Client | `Ctrl+C` in the Tauri terminal, or close the native window |
| Web Dashboard | `Ctrl+C` in the Vite/Next.js terminal |
| Marketing Site | `Ctrl+C` in the Vite terminal |

**Alternative**: Use your OS task manager / activity monitor to kill the processes:
- `pwsh`: `Get-Process | Where-Object { $_.CommandLine -like "*wrangler*" } | Stop-Process`
- `taskkill /IM tauri*` / `taskkill /IM node*`

## 2.7 Development Environment Variables

Several components read environment variables for configuration. Key variables:

| Variable | Component | Default (Dev) | Description |
|---|---|---|---|
| `PLINTH_ENV` | All | `development` | Sets environment mode |
| `JWT_PUBLIC_KEY` | Edge API | `dev_key` (per README.md) | Used for JWT verification |
| `DATABASE_URL` | Edge API | `d1:local` | D1 database connection string |
| `VITE_API_URL` | Web/Dashboard | `http://localhost:8787` | API base URL for frontend |
| `TAURI_API_URL` | POS Client | `http://localhost:8787` | API base URL for Tauri IPC |

**Setting variables temporarily**:

```bash
# Bash/zsh
export PLINTH_ENV=development

# PowerShell
$env:PLINTH_ENV = "development"

# Persist in .env file (create if missing)
# Copy from .env.example if one exists
```

**Per-component .env files**:

- `apps/edge-api/.env` - Edge API specific vars
- `apps/pos-client/src-tauri/.env` - POS Tauri vars
- `apps/web-dashboard/.env` - Dashboard vars
- `apps/marketing-site/.env` - Marketing site vars

## 2.8 Debugging Common Local Development Issues

| Symptom | Likely Cause | Resolution |
|---|---|---|
| `curl http://localhost:8787/health` returns 404 | Edge API not started or wrong port | Run `mise run dev:api`, verify port |
| POS shows "Connection refused" | Edge API not running | Start edge API first, then POS |
| Dashboard API calls return 500 | CORS misconfiguration | Check `apps/edge-api/src/router.rs` CORS config |
| Tauri command fails `invoke("submit_order")` | Rust not recompiled | Run `mise run build:pos` or `pnpm --filter pos-client exec tauri build` |
| TypeScript errors in dashboard | Type mismatch with API responses | Check `apps/web-dashboard/tsconfig.json` strict mode |
| Hurl tests return 401 | Missing auth headers | Add `Authorization: Bearer <test_token>` and `X-Store-Id: store_01` |
| Database locks during test runs | SQLite WAL mode contention | Run tests serially: `cargo test --workspace -- --test-threads=1` |
